# Runtime parity gap: what fn64 needs to replace the GPL runtime

Measured 2026-08-07 on branch `agent/static-recomp-wave-checkpoint`.

**Question.** jessetbh's six AKI ports depend on the GPL-3.0 N64ModernRuntime
family. If fn64's Rust runtime reaches parity with it, recomps built on fn64
can ship MIT. This document establishes precisely what that parity requires.

**Licensing discipline.** Every external claim below comes from public API
surface, documentation, symbol lists, and configs. No implementation code from
any GPL project was read, copied, transcribed, or paraphrased. Where this
document says what a function *must do*, that obligation is derived from the
public libultra Programming Manual and from function *signatures*, never from
another project's function bodies. The whole value of the exercise is that
fn64's runtime is independently authored; a single adapted line would destroy
it.

---

## The bottom line, stated first

**Surface parity is already achieved and slightly exceeded. Parity is
achievable, and the largest remaining item is not in the runtime at all.**

fn64 exports **139** libultra `*_recomp` shims against the **116** names in
N64Recomp's `reimplemented_funcs` list. The set difference is:

- **Missing in fn64: 0.**
- **Present in fn64 beyond the list: 23** — `__osPiGetAccess`,
  `__osPiRelAccess`, `__osSiDeviceBusy`, `__osSiRawStartDma`, `__osSpGetStatus`,
  `__osSpSetStatus`, `osDpGetStatus`, `osDpSetStatus`, `osEPiWriteIo`, the six
  `osGbpak*` Transfer Pak adapters, `osLeoDiskInit`, `osPfsIsPlug`, `osViFade`,
  `osViGetCurrentField`, `osViGetCurrentLine`, `osViGetCurrentMode`,
  `osViGetStatus`, `osViRepeatLine`.

This was computed by differencing the shim symbols exported from
`crates/fn64-abi/src/` against the machine-extracted `reimplemented_funcs`
array in `~/Code/aki-recomp/runtime/abi_surface.json`
(`symbol_lists_cpp_union.reimplemented_funcs`, 116 entries). The repo already
tracks this independently: `docs/COMPLETENESS.md:212` reports **116/116
exported, 0 partial, 0 trap, 0 absent**, generated by
`scripts/check-nmr-surface.py` from `crates/fn64-abi/nmr-surface.json`.

The four non-libultra dispatch helpers generated code calls unconditionally are
also present: `pause_self` (`crates/fn64-abi/src/dispatch.rs:21`), `switch_error`
(`:39`), `do_break` (`:59`), `get_function` (`:81`). The three helpers fn64 does
*not* export — `cop0_status_read`, `cop0_status_write`, `recomp_syscall_handler`
— have **zero call sites in both AKI games** per `abi_surface.json`'s
`a_extern_functions.recomp_h_dispatch_helpers` per-game counts, so their absence
is not an AKI blocker.

**The honest qualifier, which the repo states about itself:** surface parity is
necessary but not sufficient. `docs/COMPLETENESS.md:397-401` says so directly —
"Surface parity is therefore necessary but not sufficient for feature parity,"
and notes the repo "does not currently have an end-to-end reference-runtime
differential." Every symbol exists and none traps; whether each *behaves* like
hardware under AKI's specific demands is a separate, per-subsystem question, and
that is what the gap list below is actually about.

## A. What a recompiled N64 game requires of its runtime

Derived from the public N64Recomp/N64ModernRuntime interface surface
([N64Recomp](https://github.com/N64Recomp/N64Recomp),
[N64ModernRuntime](https://github.com/N64Recomp/N64ModernRuntime)), the
`symbol_lists.cpp` reimplemented/ignored/renamed partition, and the public
libultra [Programming Manual](https://ultra64.ca/files/documentation/online-manuals/man/).

| Category | Obligation |
|---|---|
| Dispatch helpers | Resolve an indirect call target from a 32-bit vram (`get_function`); trap a jump-table miss (`switch_error`) and a `break` (`do_break`); convert a guest self-loop into a cooperative yield (`pause_self`). |
| Threads | Create/start/stop/destroy guest `OSThread`s with priorities; a scheduler that preempts, since guest code is written for a preemptive OS. |
| Message queues | Create; blocking and non-blocking send/recv; jam (front-insert); bind a hardware event to a queue+message (`osSetEventMesg`). |
| Timers / time | Deadline-ordered timer list; virtual `OSTime` and CP0 `Count` that advance monotonically with guest execution. |
| Interrupts | A CPU interrupt mask plus the six MI RCP mask bits. |
| PI / cart | Cart handle init; async and raw DMA through a PI handle; PI status; virtual→physical translation; a PI manager serializing requests. |
| SI / PIF | The PIF-RAM command-block protocol over four Joybus channels: controller query/read, EEPROM, Rumble, Controller Pak, Transfer Pak. |
| VI | Mode/scale/special-features programming; framebuffer swap; retrace events; current/next framebuffer queries. |
| SP / RSP | Load and start an `OSTask`; yield/yielded handshake; post SP-done and, for a graphics task, DP-done to the queue the game registered. |
| RSP microcode | Execute the audio ucode and the graphics ucode — either faithfully (LLE) or by a recognized high-level implementation. |
| RDP | Rasterize the display list the graphics ucode produces. |
| AI | DAC frequency; buffer submission; length/status the game paces itself against. |
| Save media | SRAM, FlashRAM, EEPROM (4k/16k), Controller Pak — with persistence across runs. |
| Host shell | A window; present a frame; audio output device; frame pacing; player input. |

## B. What fn64 implements

Every claim below carries `file:line` from this worktree.

### Implemented and exercised by a real AKI run

- **Dispatch helpers.** `dispatch.rs:21/39/59/81`. `switch_error` and `do_break`
  are deliberately loud panics (`:39`, `:59`), never silent fallbacks.
- **Threads.** Real cooperative executor with guest `OSThread`s as coroutines.
  `crates/fn64-abi/src/thread.rs:48` (create, with OSId-collision handling),
  `:149` (start — genuinely suspends the caller so a higher-priority thread can
  preempt), `:182/203/255/276/290`. Unregistered handles panic loudly
  (`thread.rs:228`).
- **Message queues.** `crates/fn64-abi/src/mesgqueue.rs:14/33/100/171/206` —
  blocking send/recv via typed executor yields, correct NULL-msg and
  NOBLOCK-empty semantics.
- **Timers / time.** `crates/fn64-abi/src/timer.rs:30/69`;
  `crates/fn64-abi/src/system.rs:127/148/167/198`. Virtual clock by design.
- **Interrupts.** `system.rs:11/95/109` — sets both CPU Status.IE/IM and the six
  MI mask bits.
- **PI / cart.** `crates/fn64-abi/src/pi/timing.rs:728` (cart handle), `:802`
  (`osEPiStartDma`, timed through the device fabric with byte-verified `OSIoMesg`
  offsets), `:922/961/1034/1087/1115/1153`.
- **SI / PIF.** `crates/fn64-abi/src/si/mod.rs:703` — a real PIF-RAM command-block
  walker handling `0x00/0xFD/0xFE/0xFF`, EEPROM channel 4, rumble, Controller Pak
  pages, Transfer Pak, and Voice. `osContInit` (`:1180`) runs a real four-channel
  query across the timed fabric.
- **VI.** `crates/fn64-abi/src/vi.rs:66` (full `OSViMode` decode into 14
  registers), `:111/127/143/161/176/366/393`.
- **SP / RSP task.** `crates/fn64-abi/src/task_dispatch/lifecycle.rs:867`
  (`osSpTaskLoad`), `:977` (`osSpTaskStartGo` — classifies boot-overlay vs
  direct-IMEM, runs the task, and posts SP-done plus DP-done for `M_GFXTASK`),
  `rsp_commit.rs:1387` (`osSpTaskYielded`).
- **AI.** `crates/fn64-abi/src/ai.rs:47/105/131/173`.
- **RSP audio, LLE, clean-room.** `crates/fn64-audio/src/rsp/` — scalar+VU
  interpreter, MIT by necessity since the GPL `librecomp/rsp.hpp` cannot be
  depended on (`docs/WM2000-AUDIO-STATUS.md:7-11`). The AKI family ships one
  shared 3,156-byte audio ucode, byte-identical across all five titles
  (`WM2000-AUDIO-STATUS.md`, "WM2000 audio execution"). A guarded run completed
  **985 audio tasks**, delivered 984 buffers / 1,031,872 samples with 459,481
  nonzero, all reaching a live cpal device.
- **Graphics.** Reference software rasterizer `crates/fn64-render-reference/`
  (~38k lines) plus an RT64 backend in a separate lane. Microcode identity is
  derived from pinned **MIT** RT64 recognition rows, not GPL sources
  (`crates/fn64-render/src/microcode_identity.rs:1-11`).
- **Save media — all five device types with real host-file persistence.**
  `crates/fn64-runtime/src/save.rs:121` (`SaveType`: Eeprom4k, Eeprom16k,
  SramBanked, FlashRam, ControllerPak), `:223-234` (sizes), `:370`
  (`FileSaveStorage::open_for_device`), `:375-405` (real seek/read/write to a
  host file). EEPROM `crates/fn64-abi/src/save.rs:141-330`; Flash, all 13,
  `:374-660`.
- **Controller Pak filesystem.** `crates/fn64-abi/src/pfs.rs:182-430` over
  `crates/fn64-runtime/src/pfs.rs:169` — genuine redundant-FAT checksum
  validation and single-copy repair; ambiguous damage returns `Inconsistent`
  rather than inventing data.
- **Rumble.** `crates/fn64-abi/src/si/mod.rs:1372/1400/1439/1449/1460`.
- **Host shell — and it has presented thousands of real frames, on OoT.**
  `crates/fn64-shell/src/main.rs` is a real `winit` window with a `pixels`/wgpu
  presenter (`:99-105`), blitting the live VI framebuffer every swap
  (`:534-608`, with the correct `(2*i) ^ 2` halfword swizzle and a per-row
  `src_stride` from real `VI_WIDTH` so non-320-wide modes do not shear), a
  file-backed save (`:250`, `:138`), live keyboard+gamepad input (`:480-481`),
  a cpal audio device requesting the guest's own 32 kHz rate (`:1006-1039`),
  and non-blocking 60 Hz wall-clock pacing (`:872-920`).

  It drives the executor itself — ROM load, IPL3 seed, section registration,
  `boot_thread0`, then `run_one_step` in a drain loop (`:216-413`, `:483`). It
  is not a replay viewer. `docs/OOT-STATUS.md:19-20` records **4,200+ VI swaps**
  with controllable gameplay, and `:149-158` records ten consecutive release
  probes each reaching 250 swaps with a non-uniform framebuffer.
  `docs/ROADMAP.md:254-258` contains a live per-swap heartbeat series (swap #60
  through #480) that only the shell's post-present path can emit.

**Two harnesses, and the distinction matters below.** `crates/fn64-shell` is the
general shell above; `examples/wm2000-block-boot` is a separate WM2000-specific
headless/windowed harness — it is what `run-wm2000.sh:21` launches, it owns
`FN64_CONTROLLER_SCHEDULE`, and it uses `InMemorySaveStorage`
(`examples/wm2000-block-boot/src/main.rs:793`). Nearly every recorded WM2000
number comes from that lane, not from `fn64-shell`.

### Deliberate, documented no-ops (correct, not gaps)

- Cache ops — `crates/fn64-abi/src/cache.rs:16/27/36/47`. fn64's RDRAM is a flat
  coherent buffer, so cache maintenance has no architecturally visible effect
  (`cache.rs:8-11`).
- `osCreateViManager` (`vi.rs:33`), `__osPiGetAccess`/`__osPiRelAccess`
  (`pi/timing.rs:1008/1018`), `osCreatePiManager` (`:986`, registers the queue
  only) — the single-executor model has no separate manager thread or PI-bus
  contention to arbitrate.

### Where the AKI-family hazards actually stand

The prior comparison (`docs/plans/n64recomp-comparison.md`) flagged two shared
hazards. Both have moved since it was written.

- **The idle-thread busy-spin that starves a cooperative scheduler.** Their
  configs patch this family-wide. fn64 does not need the patch: the executor
  preempts on an instruction budget (`Yield::InstructionCheckpoint`,
  `crates/fn64-runtime/src/executor/mod.rs:1637`) rather than relying on
  voluntary yields, and WM2000 routes report `idle_steps=0` throughout
  (`docs/plans/wm2000-playable-blocker-ledger.md:1730`) while taking 4,477
  controller reads. **Not a gap.**
- **The music-sequence assert that parks a thread forever.** The prior doc
  called this unmitigated in fn64. It is no longer. `dispatch.rs:15-22` records
  fn64 hitting this exact bug independently (the sound driver's file-id bounds
  assert at `0x80003DF0`, an out-of-range id `0xC5BE` indexing past the file
  tables and submitting a PI DMA sized `0xFFFFFFFC`) and fixing it by parking
  the thread as `Stopped` rather than resuming at the following host statement
  (`executor/mod.rs:1623-1635`). **Closed.**

## C. The gap list, ranked by what blocks "fully playable" for AKI

Ranked by distance from a playable match, not by size.

### Gap 1 — WM2000 has never presented a frame in `fn64-shell`

**This is the largest single item, and it is integration, not runtime API.**

Two facts that look contradictory are both true, because they are different
lanes.

**In the headless route harness, WM2000 draws the game.** It renders its **match
setup screen** — Exhibition / Single Match / 1P VS 2P / New Belt / Non Title
Match / Controller Pak — captured at frame 1,599 of a 1.5M-step scheduled route
and committed at `reference/wm2000-frames/match-setup-screen.png`
(`docs/plans/wm2000-playable-blocker-ledger.md:1717-1733`). 2,239 frames dumped
in one run, `idle_steps=0`, `render_error=None`. A live, textured, layered game
UI drawn by the recompiled program.

**In `fn64-shell`, it has never presented.** `docs/BOOT-NOTES-WM2000.md:945-951`
records a 100-second probed shell run in which `current_vi_framebuffer()` never
became `Some`, the `[fn64-shell] presenting VI framebuffer (swap #N)` line never
appeared, and zero raw SP-register writes were observed — the white window was
the unpresented macOS default surface, not game output. That note explicitly
retracts earlier optimism. So `vi_swaps=0` **is** true and current for
WM2000-in-shell, even though it is false for the shell generally (OoT: 4,200+
swaps) and false for WM2000 in the route lane (2,239 frames).

The shell-lane frontier is documented at `docs/BOOT-NOTES-WM2000.md:952-955`:
boot reaches the steady 60 Hz retrace loop, threads 0/1 return cleanly, and
threads 3 and 6 sit on a queue/retrace cascade.

Also unproven in **any** lane: a **match in progress** — the entrance
presentation and the arena (`wm2000-playable-blocker-ledger.md:1731-1733`). The
probes already exist: the selector gate word at `0x8003dd0c` and the four
match-arena loader PCs `0x80022484`, `0x80022498`, `0x800224d4`, `0x80022510`
(`:1711-1714`). And the other four AKI titles have passed CPU recompilation with
`unsupported=0` (`docs/plans/aki-recompile-certification.md:18-24`) but have
never been booted at all.

*Entails:* reconcile the two lanes — the route harness proves the recompiled
program and renderer work, so the shell gap is in boot/dispatch wiring, not in
the runtime API. Then run the arena probes, then boot the other four titles.
This is what converts "surface parity" into "parity."

### Gap 2 — Save type is hardcoded to SRAM; No Mercy needs FlashRAM

The machinery is complete but the *selection* is not. Every call site hardcodes
`SaveType::SramBanked`: `crates/fn64-shell/src/main.rs:147` and `:162`,
`examples/wm2000-block-boot/src/main.rs:794` and `shell.rs:445`. There is **no
save-type autodetection** from the ROM anywhere — no header field, heuristic, or
database.

This matters because the AKI family is *not* uniform in save media, per each
port's own README: WM2000 uses cart save **plus Controller Pak**, No Mercy uses
**flash**, VPW2 uses **SRAM** (256 Kbit), VPW64 and World Tour use **Controller
Pak** ([No Mercy](https://github.com/jessetbh/WWFNoMercyRecomp),
[VPW2](https://github.com/jessetbh/VPW2Recomp),
[World Tour](https://github.com/jessetbh/WCWvsNWOWorldTourRecomp)). Booting No
Mercy today would hand a flash-driver game a 32 KiB SRAM device.

There is also **no environment override** — `FN64_SAVE`, `FN64_SRAM`,
`FN64_FLASH`, `FN64_EEPROM`, `FN64_PFS`, `FN64_MEMPAK` have zero hits
repo-wide. The backend is a compile-time choice plus a hardcoded
`dirs::data_dir()/fn64/saves/<rom-stem>.sav` location
(`crates/fn64-shell/src/main.rs:123-132`).

Two related notes. First, only `fn64-shell` installs `FileSaveStorage` at all;
every example harness uses `InMemorySaveStorage`, and `examples/oot-boot/src/main.rs:322`
states the intent — "a persisted `FileSaveStorage` is a shell concern, not this
bring-up's." So every run that has ever reported a `save_ops` figure was
in-memory-backed. Second, SRAM has **no** high-level shim family: it is reachable
only as PI Domain 2 traffic via `osPiStartDma`/`osEPiStartDma`
(`crates/fn64-runtime/src/device/mod.rs:402-432`, commit at
`device/fabric_ops.rs:839`), which is architecturally correct but means SRAM
titles depend on the PI path rather than a dedicated shim.

*Entails:* a save-type resolution step (per-title override at minimum;
ROM-database or heuristic detection preferably) feeding the existing
`SaveType`. The device implementations already exist. Small.

### Gap 3 — Controller Pak is never persisted and never attached by the shell

`ControllerPak` images are per-port and in-memory, created on demand when a port
is set to `StandardControllerControllerPak`
(`crates/fn64-runtime/src/peripherals.rs:106`, `:268-271`, `:286-289`).
`crates/fn64-runtime/src/pfs.rs` contains **no** host-file path — no `std::fs`,
no `File`. And `fn64-shell` never attaches one: it wires exactly one save store
(`main.rs:250`) and never calls `attach_controller_pak` or sets any port to a
Controller Pak state.

This is directly visible in the game: WM2000's match setup screen renders a
**Controller Pak** option, and the run reports `save_ops=0` for its whole
duration (`docs/plans/wm2000-playable-blocker-ledger.md:825`).

**Read `save_ops=0` carefully** — it counts save-device operations the *guest
performed*, not fn64's ability to service them (`copy_save_operations`,
`crates/fn64-abi/src/lib.rs:1521`, emitted at
`examples/wm2000-block-boot/src/telemetry.rs:353`). The guest has not asked yet.
It is evidence the path is **unexercised**, not that it is missing — an
important distinction, because three of the four AKI titles save to Controller
Pak.

Note the asymmetry this creates: `osPfsReadWriteFile` calls
`record_save_operation(SaveType::ControllerPak, ...)`
(`crates/fn64-abi/src/pfs.rs:450`), so the trace reports a save happened while
nothing durable exists. There is an `evidence_snapshot()`
(`crates/fn64-runtime/src/pfs.rs:145`) exposing the raw bytes, but it feeds only
the release-gate digest, not a user-facing file.

A second consequence: port 0 defaults to `StandardControllerNoPak`, which does
**not** set `CONT_CARD_ON` (`crates/fn64-runtime/src/si.rs:202-205`), so
`osPfsIsPlug` returns a bitpattern of 0 out of the box
(`crates/fn64-abi/src/pfs.rs:218`). A game probing for a pak is correctly told
there is none.

*Entails:* attach a Controller Pak to port 0 in the shell (set the port state to
`StandardControllerControllerPak`), and give `ControllerPak` a file-backed store
alongside the existing `FileSaveStorage`. Small; the FAT/note-directory logic is
done.

### Gap 4 — Multiplayer input: ports 1-3 are modeled but never populated

The runtime models all four ports properly — `ports: [PortState; 4]`,
`inputs: [ContInput; 4]`, `rumble_on: [bool; 4]`
(`crates/fn64-runtime/src/si.rs:95-97`, `:107-126`), with a per-port setter
(`:150`) and per-port input (`crates/fn64-runtime/src/executor/mod.rs:1181`).
Ports 1-3 simply **default to `Absent`** (`si.rs:119-125`), and
`set_port_state` is called only from tests — no host or shell path populates
them.

The shell is structurally single-player: `Gamepads::resolve`
(`crates/fn64-shell/src/gamepad.rs:96`) returns one merged `(buttons, x, y)`
across every connected pad, and the caller sends it to port 0 only —
`fn64_abi::set_controller_state(0, buttons, sx, sy)`
(`crates/fn64-shell/src/main.rs:481`, merge at `:518-530`).

For AKI titles this is load-bearing: WM2000's setup screen offers **1P VS 2P**,
and World Tour ships 4-player local multiplayer. Worth noting this is also where
*their* polish ends — WM2000 and No Mercy both document that 2+ player sessions
"can crash in certain modes." So this is a place fn64's typed per-port fabric
could plausibly beat the GPL runtime rather than merely match it.

`Gamepads` does enumerate multiple pads and supports hotplug
(`gamepad.rs:31-35`, `:63-73`), but tracks a single `active` pad — "first press
wins; a different pad becomes active by being used" (`gamepad.rs:19-21`). So
multiple pads are detected and one is played.

**Rumble is a related half-gap.** The guest-side model is complete — `osMotor*`
shims (`crates/fn64-abi/src/si/mod.rs:1372-1460`), the raw Joybus `0x03` path
writing the same latch (`:356`), typed `NoPak`/`WrongDevice` discrimination
(`crates/fn64-runtime/src/si.rs:160-171`), and a host readback seam
`fn64_abi::rumble_active(port)` (`si/mod.rs:823-825`) documented "for a host
haptics backend." But **nothing calls it outside tests** — there is no gilrs
force-feedback in `crates/fn64-shell/src/gamepad.rs`. Rumble is modeled
correctly and terminates at the ABI boundary.

*Entails:* map each gilrs pad to a port index, set those ports present, route
per-port input, and connect `rumble_active` to gilrs force-feedback. The runtime
side needs nothing. Small-to-moderate, and entirely in `fn64-shell`.

### Gap 5 — Behavioral residuals inside shims that do exist

Real implementations with acknowledged simplifications. None is known to block
AKI; each is a candidate cause if a specific title misbehaves.

- **PIF command coverage.** Unimplemented PIF command bytes record an unsupported
  event and panic (`crates/fn64-abi/src/si/mod.rs:59-80`). Controller Pak
  **management-page inode/directory decoding over raw Joybus remains open**, and
  several Voice command forms trap (`:684-686`). The high-level `osPfs*` path is
  complete; a game driving the pak through raw SI could hit this.
- **Flash is synchronous and single-chip — the weakest family, and No Mercy is
  the flash title.** Reads/writes/erases are real
  (`crates/fn64-abi/src/save.rs:608/575/503/480`), but four entry points are
  thinner than the rest of the ABI: `osFlashReadStatus` (`:396`) returns a status
  word that is always clear because all mutations complete synchronously
  (`:390-391`); `osFlashReadId` (`:413`) returns a constant identity
  (`FLASH_TYPE_1MBIT`/Macronix, `:24-25`) unless the host overrides it;
  `osFlashCheckEraseEnd` (`:537`) hardcodes success and can never report failure;
  and `osFlashChange` (`:652`) asserts `flash_num == 0` and otherwise does
  nothing. `osFlashInit` (`:374`) also requires the embedder to have registered a
  handle VRAM and panics otherwise. A game that polls flash status through an
  erase cycle, or checks the chip id, may behave differently than on hardware.
  **This is the one place where "116/116 implemented" most overstates behavioral
  readiness, and it sits directly under a target title.**
- **`osSpTaskYield` is one status-bit write** (`lifecycle.rs:1355`). It sets
  `SP_SET_YIELD` but does not interrupt in-flight RSP work. AKI submits several
  RSP tasks per visual frame, so this is worth watching.
- **`osContSetCh` timing is unverified** (`si/mod.rs:1290`, stated in its doc).
- **`osInitialize` is partial** (`system.rs:57`) — FPCSR and AI only; exception
  vectors and debug TLB are deliberately executor responsibilities (`:37-45`).
- **Absent symbols outside the 116 denominator:** `osYieldThread`, `osPfsChecker`,
  `osDriveRomInit`, `osPfsNumFiles`, `osPfsRepairId`, `osAfterPreNMI`. None is in
  `reimplemented_funcs`; jessetbh's WM2000 config routes `osDriveRomInit` to a
  runtime shim and it is meaningless on cart (`docs/BOOT-NOTES-WM2000.md:341`).
  Cheap to add if a title ever calls one.

### Gap 6 — No end-to-end differential against a reference runtime

`docs/COMPLETENESS.md:399-401` states this plainly: behavior known only from
N64ModernRuntime "must be established by a black-box differential experiment,
never by reading GPL implementation bodies," and the repo "does not currently
have an end-to-end reference-runtime differential."

This is the methodological gap that keeps every claim above at *surface* parity.
It is also the one gap whose solution is constrained by licensing: the
experiment must be black-box — same ROM, same input schedule, compare observable
outputs — and must never involve reading their implementation.

### Scoping note: what `vi_swaps=0` does and does not mean

The premise that "no fn64 window has ever presented a frame" is **false as a
general claim and true in one specific lane**. Three distinct readings:

- **`fn64-shell` generally: false.** OoT has reached 4,200+ VI swaps with
  controllable gameplay (`docs/OOT-STATUS.md:19-20`), plus ten consecutive
  250-swap release probes (`:149-158`) and a live heartbeat series
  (`docs/ROADMAP.md:254-258`). The window, blit, audio, and pacing are proven.
- **WM2000 in `fn64-shell`: true, and current.**
  `docs/BOOT-NOTES-WM2000.md:945-951` — that is Gap 1.
- **WM2000 in the route harness: false.** 2,239 frames,
  `render_error=None` (`wm2000-playable-blocker-ledger.md:1717-1733`).

One further citation is a red herring worth retiring: the `vi_swaps=0` string
in `crates/fn64-abi/src/task_dispatch/tests/dispatch_c.rs:284-296` is a **fixed
regression test's docstring** describing a closed OoT deadlock
(`osSpTaskStartGo_recomp` failing to post SP-done/DP-done, so `osViSwapBuffer`
was never reached). The test now guards against its reintroduction. Similarly,
`wm2000-playable-blocker-ledger.md:8-22` retracts an earlier `gfx_submits=0`
claim as a harness artifact (a missing `FN64_CONTROLLER_SCHEDULE`).

## D. Is parity achievable, and what is the largest item?

**Yes — and fn64 is closer than the framing of this question assumed.**

On the runtime API surface that a recompiled AKI game actually links against,
fn64 is **already at parity and slightly ahead**: 116/116 of the GPL runtime's
reimplementation surface, plus 23 beyond it, plus all four hot dispatch helpers,
with zero traps and zero absences. There is no missing subsystem. Threads,
message queues, timers, interrupts, PI, SI/PIF, VI, SP, AI, RSP audio (LLE,
clean-room MIT), rasterization, all five save device types with host-file
persistence, the Controller Pak filesystem, and rumble are all implemented, and
a real windowed shell with gamepad input and audio output exists.

**The largest single item is Gap 1: WM2000 has never presented a frame in
`fn64-shell`.** It is the largest not because it is the most code — it is
probably the least — but because it is the only one that converts a surface
claim into a behavioral one, and because it is the only gap where two lanes
already disagree. The route harness proves the recompiled program, the RSP audio
stack, and the rasterizer all work on WM2000 (2,239 frames, match setup screen
drawn); `fn64-shell` proves the window, blit, audio device, and pacing all work
on OoT (4,200+ swaps). **Both halves exist and have never been joined on the
same title.** That strongly suggests the shell gap is boot/dispatch wiring
rather than a missing runtime capability — which is exactly the kind of gap that
does not threaten the licensing thesis.

The gaps between today and "five AKI titles fully playable," in order:

1. Join the two lanes — get WM2000 presenting in `fn64-shell`; then drive it past
   match setup into a match; then boot the other four titles.
2. Resolve save type per title (No Mercy is flash, not SRAM) and firm up the
   flash status/id/erase-completion paths that title will exercise.
3. Attach and persist a Controller Pak (three of the five titles use it).
4. Route per-port input so 1P VS 2P and 4-player work, and connect rumble output.

None requires new runtime architecture. That is the finding: **the parity that
licenses MIT recomps is essentially already built; what is missing is the
evidence that it works end-to-end, plus roughly four small pieces of shell
wiring.**

A closing caution, in the repo's own spirit: this document establishes *surface*
parity with citations and *behavioral* parity only as far as WM2000's match
setup screen. Gap 6 exists precisely because the difference between those two
cannot be closed by reading anyone's source — only by running both and comparing
outputs.
