## THE OPEN PROBLEM (the owner's live complaint)

**"it's laggy and bg music is still choppy"** — said while playing the newest
build, the one that is verified fastest headless. This is the single most
important open thread.

The contradiction is the finding:

- **Headless block lane: 15.69 ms/field, 0.94x the 60fps budget**, byte-identical
  8/8 on the 1.5M route (lane B, below). The emulation core is *under* budget.
- **Windowed shell, same tree, same rt64 renderer: frame_interval p50 34–42 ms**
  with p99 spikes to 110–237 ms, and `pump_ms` p50 climbing 12.7 → 29.1 ms
  across consecutive heartbeat windows *within one session*.

Two things that pattern implicates, neither yet investigated:

1. **`pump_ms` rises monotonically over the session** (12.7 → 13.6 → 22.5 →
   24.8 → 29.1 across five consecutive heartbeats). The headless route is
   short-lived; a long window session is not. Prime suspect: the **unbounded
   `host.rsp_rdp_observations` vector** (`fn64-abi/src/lib.rs:1570`, ~2.8
   pushes/field, cleared only on ROM load). The release gate reads *all* of it
   (`release_gate/evidence.rs:183-201` digests the whole ordered sequence and
   asserts `total_observations == ordered.len()`), so it cannot simply be
   capped — it needs a streaming/rolling digest design change. **Falsifier:**
   watch RSS and `pump_ms` together over a 10-minute session; if RSS climbs in
   step with pump_ms, that's it.
2. **Audio choppiness is a separate symptom with its own evidence.** The device
   rejects 32 kHz and opens at 48 kHz with band-limited resampling
   (`fn64-audio` logs this at startup). Sample counters advance healthily
   (`ai_buffers` and `backend_buffers` stay equal, ~57k samples/heartbeat), so
   the ring is being fed — the choppiness is more likely underrun *timing*
   caused by the same pump stalls than by the audio path itself. Verify before
   fixing: correlate audio glitches against the `pump_ms` p99 spikes.

**Do not start by optimizing the renderer.** The headless number says the
renderer is fine. Start by explaining the divergence between 15.69 ms headless
and 34–42 ms windowed, and the within-session drift.

## Today's commits, and what each actually established

Six render commits, all on the raw-RDP lane. **They are five correct spec fixes
that turned out to share one root cause** — worth understanding as a unit:

- `172c866`, `122b4d4`, `1ccaf25`, `7ece9cf`, `51c439b` — RDP opcodes 0x01–0x07
  are No Operation; the command field is **6 bits** (bits 61:56, so 0x7f masks
  to 0x3f = Set Color Image); No Operation marks every bit don't-care but
  `command[5:0]`; a FILL-cycle texrect behaves as Fill Rectangle; `G_SETCIMG` is
  a latch like `G_SETTIMG`. Each is right against the public command table.
- `d61af47` — **the actual root cause.** Task #657's display list ends at byte
  3,280 of a 65,376-byte submitted range; everything after `SyncFull` is the
  previous frame's stale buffer. The guest legally declares the wide `DPC_END`
  (bookkeeping audited and exonerated: every range starts at `0x3eefd0`, and a
  51-command range following an 8,165-command one proves it is not a high-water
  mark). Hardware consumes the residue harmlessly because the stale target sits
  at 15.5 MiB, where per N64brew "no Rambus device will respond" and "writes
  will be ignored." So: execute the residue with documented dropped-write
  semantics; strictness unchanged for addresses that exist.

Six No Mercy commits, each one layer deeper (memory map → device type →
declaration → declaration lifecycle):

- `14fe327` — No Mercy is **FlashRAM**, not the template's SRAM; handle vram is
  `0x800b8448` (**not** `0x800b8454` — that's the `baseAddress` field at +12,
  and wiring it would write every field 12 bytes high).
- `fbffd23`, `6051aff`, `bcc0586` — `osEPiWriteIo`/`osEPiReadIo` recognized as an
  optional non-gating role, wired through the shard generators, resolved to
  runtime shims. 287-ROM sweep, zero false positives.
- `7d2f13f` — the flash API bound so the guest driver never runs. The surface is
  **3 roles, not 13** (`osFlashInit`, `osFlashSectorErase`, `osFlashReadArray`);
  the other 10 have zero references in the whole 32 MB ROM.
- `db6a3ad`, `973b83b` — writer attribution. `notify_host_abi_write` is only
  *half* the protocol: something must drain
  `PENDING_ATTRIBUTED_EXECUTABLE_WRITES` before an ordering boundary. Added
  `declare_guest_physical_write` supplying the missing half (child transaction +
  commit) while callers keep their swizzled `RdramPtr` writes — routing them
  through the flat `write_guest_physical` would have silently reordered every
  save transfer.
- `efb91bd` — RSP/RDP evidence digests batched. Honest accounting: worth ~0.04
  ms/field, an order of magnitude below the prediction. Its real value is two
  correctness findings: `RdramPtr::read_u8` applies a `^3` lane swizzle, so
  naive slice-chunking **would have silently changed `data_sha256`** in gate
  evidence; and the release gate requires *every* observation, so the unbounded
  vector cannot be capped without a gate-side redesign.

## Pre-existing failure, not yours — RESOLVED, and the diagnosis was wrong

`fn64-abi frame_census::the_spread_rows_distinguish_a_spiky_phase_from_a_flat_one_at_equal_mean`
was recorded here as wall-clock sensitive, confirmed independently by three
agents on a stashed tree. **It is not wall-clock sensitive.** The test builds
forty entirely synthetic samples with hardcoded 2ms/18ms phase costs and never
reads a clock, so it cannot be timing-dependent.

It was reading the wrong bucket. Every sample is 40 ms, so the 16.667 ms
partition puts all forty in `slow` and leaves `fast` empty; the report emits a
row set per bucket with `fast` first, and a bare `.find()` matched the empty
one. The census itself was correct throughout — it reports the 9.0x dispatch
spread and 1.0x cop0 spread the test asks for. Fixed to select `slow`
explicitly.

**Method note worth keeping:** "three agents confirmed it" established that the
failure *reproduced*, not that the stated cause was right. Reproducibility and
diagnosis are different claims, and a label attached to the first travels as if
it were the second. The symptom that broke it open was `p50=0.000 p95=0.000` —
an *empty* measurement, where a timing-sensitive test gives wrong ratios rather
than zeros.
