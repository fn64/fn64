# Mechanical Function-Metadata Discovery for N64 ROMs

Status: design note  
Date: 2026-07-14

## Executive summary

Given a new N64 ROM, we can make function-metadata discovery mechanical,
deterministic, parallel, cacheable, and fail-closed. We cannot guarantee that
static analysis will prove every real function in every stripped ROM. Some
ROMs contain unreachable code, runtime-built function-pointer tables,
overlapping overlays, handwritten assembly, or data that decodes as valid
MIPS.

The correct output is therefore never just a guessed symbol file. It is:

```text
proven metadata + rejected candidates + an explicit unresolved frontier
```

Every accepted fact carries evidence. Anything the machinery cannot prove is
preserved as `candidate`, `conflict`, or `open`, rather than silently promoted.
This produces useful metadata early while making uncertainty visible and
actionable.

NW4E already has unusually strong bank-qualified function ownership. This
document describes the generalized onboarding pipeline needed to obtain the
same kind of evidence efficiently for a new N64 ROM.

## Goals

- Discover function ownership and callable entries without requiring semantic
  names.
- Treat overlays and other load images as first-class identities.
- Reuse static analysis, known-library signatures, dynamic traces, and exact
  assembly validation without making any single detector authoritative.
- Produce deterministic, provenance-bound Target Pack and Decomp Pack inputs.
- Support incremental analysis: changing one bank or evidence decision should
  not require reanalyzing the entire ROM.
- Allow unrelated functions to enter the matching-decompilation queue while
  difficult indirect-call sites remain explicitly open.
- Require machine-verifiable proof for every promoted conclusion.

## Non-goals

- Recovering original semantic names automatically.
- Recovering original source files or translation-unit boundaries as a
  prerequisite for decompilation.
- Producing clean, idiomatic C automatically.
- Claiming that dynamic coverage proves all possible execution paths.
- Treating a confidence score as proof.
- Building a universal N64 emulator as part of the analysis engine.

## Required function metadata

Every accepted function is identified by `(profile, bank, entry_pc)`, never by
PC alone. Its record should contain at least:

```text
profile and bank
entry PC
end PC, exclusive
ROM start and end
runtime VA mapping
basic-block starts
direct calls and tail transfers
indirect call sites
proven and observed indirect targets
interior callable entries
original-byte digest
evidence records
proof status
```

Semantic names are optional aliases. Stable generated names are sufficient for
mechanical work:

```text
n64_resident_80001234
n64_overlay_03_80106760
```

Function-pointer targets are required only as they become dependencies. A
caller can enter matching decompilation once the symbols, relocations, and ABI
facts that affect that caller are resolved. It does not need to wait for every
function-pointer table in the ROM.

## Result classifications

The analysis should use discrete proof states rather than one blended
confidence number:

- `proven`: accepted by a defined proof rule and eligible for authoritative
  output.
- `supported`: corroborated by independent evidence but not yet sufficient for
  authoritative promotion.
- `candidate`: generated by a heuristic or detector.
- `conflict`: incompatible evidence or multiple valid interpretations exist.
- `rejected`: contradicted by stronger evidence.
- `open`: required fact remains unresolved.

Dynamic observations must also distinguish existence from exhaustiveness. An
observed indirect target proves that the target occurred; it does not prove no
other target is possible.

## Pipeline overview

```text
ROM normalization
       |
       v
load-image and overlay discovery
       |
       v
candidate code discovery
       |
       v
CFG and dataflow closure
       |
       v
function partitioning
       |
       v
indirect-target closure
       |
       v
assembly/relink verification
       |
       v
proven pack + unresolved frontier
```

## Phase 1: normalize and identify the ROM

Mechanically:

1. Detect `.z64`, `.v64`, or `.n64` byte order.
2. Convert to canonical big-endian bytes.
3. Record SHA-256, SHA-1, and MD5 identities.
4. Parse the ROM header, entrypoint, and boot region.
5. Identify the CIC where possible.
6. Reject malformed or unexpected inputs before analysis.

All downstream artifacts and cache keys must bind to the normalized ROM
digest.

## Phase 2: discover load images before functions

> Implementation status (D1.5, 2026-07-16): Phase 2 now accepts an explicit,
> generalized range-table shape: table location in physical ROM or VROM,
> record count/stride, configurable source start/end fields in ROM or VROM,
> and configurable destination start/end fields in physical ROM or VRAM.
> A destination end may be explicit, derived from source length, or use the
> file-table convention where a zero end means an uncompressed equal-length
> file. The same mechanism therefore represents VROM file tables,
> VROM-to-VRAM overlay tables, and physical-ROM descriptor tables; the older
> `DescriptorTableInput` remains supported. Table locations and bank naming
> are caller-supplied data, never guessed by a detector.
>
> Every parsed record is a typed `LoadImageTableRecord` fact naming its table
> and record index, with an independent proof-state conclusion. A proven
> overlay bank's `RomMapping` conclusion cites that record and, for VROM, the
> proven file-table record that supplies its bytes. Physical file mappings are
> validated against normalized-ROM bounds; compressed VROM files are
> deterministically materialized with a bounded decoder derived from the
> allowed N64Recomp-generated `Yaz0_DecompressImpl` C, and the stream's
> declared size must match the VROM interval. Malformed/blank records are `rejected`,
> missing backing is `open`, and records whose source and destination ranges
> conflict are moved to `conflict` (including every member of a multi-record
> conflict), so none can feed Phase 3 as proven input.
>
> `gate_d1` supplies OoT NTSC 1.0's file, effect, actor, gamestate, and
> Kaleido/player table geometry as shape/data input. Proven records are 1,509
> file mappings, 36 effect images, 426 actor images, four gamestate images,
> and two Kaleido images; blank/sentinel table slots remain rejected. Together
> with the boot copy this yields 469 proven load images. The input geometry is
> cited to allowed N64Recomp-generated C/section data (`DmaMgr_Init`'s file
> table load, the generated code-section VROM/VRAM mapping, and the table
> consumers' field loads/counts/strides), not to the grading key. `dump.toml`
> is opened only after discovery.

A ROM offset is not inherently tied to one runtime address. Discover candidate
ROM-to-RDRAM mappings from:

- The initial boot copy.
- PI DMA operations and descriptors.
- Constant ROM/RAM source-destination pairs.
- Overlay descriptor tables.
- Compression and decompression destinations.
- Runtime PI DMA traces.
- ROM regions repeatedly loaded into shared virtual-address ranges.

Each distinct mapping becomes a bank or load image with:

```text
bank identity
ROM interval
runtime VA interval
activation evidence
co-residency and exclusivity constraints
```

Function identity must be bank-qualified from the first instruction. Flat
function discovery followed by later overlay repair creates ambiguous symbols,
invalid edges, and address collisions.

## Phase 3: harvest candidates

> Implementation status (D1, 2026-07-16): `fn64-discover::harvest` now runs
> three zero-LLM providers concurrently over immutable, Phase-2-proven load
> images: (1) a linear `jal` scan plus bounded HI/LO-resolved `jalr` targets,
> with the call site retained as evidence; (2) classic
> `addiu`/`daddiu $sp,$sp,-N` + in-frame `sw $ra` prologues and the stricter
> leaf variant requiring a matching stack restore at `jr $ra`; and (3)
> `TableEntry` facts exposed by an already-identified descriptor table or
> vector. The third provider does not scan blindly for table locations.
> Providers return immutable claims; the merge sorts and deduplicates before
> touching `FactDb`, so host thread scheduling cannot affect serialized
> output. Independent positive providers produce `supported`; any positive
> versus rejected/conflicting provider evidence produces `conflict`, never a
> winner chosen by detector order. Only a merged `proven` entry can seed
> `resolve::build_cfg_closed_with_facts` and the existing partitioner;
> `candidate`/`supported` prologues cannot silently become authoritative
> owners.
>
> The grading-only `gate_d1` compares logical `(ROM/VROM offset, runtime VA)`
> identities after discovery, so overlapping overlay VAs cannot earn false
> matches. Against the zeldaret-derived OoT key (472 sections / 13,358
> function rows), the pre-D1.5 boot-only baseline was:
> direct/resolved calls produce 147 candidates, 85 matches, 57.823129%
> precision, and 0.636323% recall; prologues produce 76 candidates, 72
> matches, 94.736842% precision, and 0.539003% recall; the table provider has
> no OoT input facts and therefore emits 0 candidates; the combined union is
> 175 candidates / 109 matches, 62.285714% precision, and 0.815990% recall.
> With D1.5's Phase-2 table inputs, direct/resolved calls produce 5,486
> candidates / 4,505 matches, 82.118119% precision, and 33.725109% recall;
> prologues produce 8,637 / 8,612, 99.710548% precision, and 64.470729%
> recall; table-derived remains an honest zero because load-image records do
> not prove function entrypoints; the combined union is 10,667 / 9,661,
> 90.569045% precision, and 72.323701% recall. Three positive call claims fall
> in the VRAM-only tail beyond their images' VROM bytes and are reported as
> ungradable. The remaining recall frontier is primarily Phase 3 detector
> coverage inside known images plus the resident `code`/`n64dd` images, whose
> VRAM destinations are not supplied by these overlay/file tables.
> Recursive entrypoint traversal, branch/tail roots, callback discovery,
> signatures, external-tool providers, dynamic PCs, and unresolved-interval
> linear decoding remain design-only.

Run independent candidate providers in parallel:

- Recursive traversal from the ROM entrypoint.
- Direct `jal` targets.
- Direct branch and tail-jump targets.
- Exception, interrupt, thread, and callback entrypoints.
- Valid code pointers in proven tables.
- Known libultra and compiler-library signatures.
- spimdisasm function, pointer, and symbol candidates.
- Linear MIPS decoding over unresolved intervals.
- Dynamically observed PCs and indirect targets.

spimdisasm provides useful matching-assembly, function-detection, pointer,
HI/LO-pairing, and file-boundary machinery. Its same-VRAM overlay support is
experimental, so it should remain a candidate provider while the bank model
owns identity:

<https://github.com/Decompollaborate/spimdisasm>

`n64sym` can scan against known libraries and object files. Its hits are also
candidates until exact address, byte, and callsite evidence validates them:

<https://github.com/shygoo/n64sym>

Each claim records its origin rather than overwriting earlier claims:

```json
{
  "address": {"bank": "overlay_3", "pc": "0x80101234"},
  "claims": [
    {"kind": "direct_jal_target", "source_pc": "0x80014560"},
    {"kind": "signature_match", "library": "libultra_d"},
    {"kind": "dynamic_entry", "trace": "boot-001"}
  ]
}
```

## Phase 4: construct the CFG

Build delay-slot-aware basic blocks. The decoder and control-flow engine must
understand:

- Branch and jump delay slots.
- Branch-likely annulment.
- `jal`, `jalr`, and `jr`.
- Tail transfers and returns.
- Exception-producing instructions.
- Computed jumps.
- Ordinary fallthrough.
- Calls to interior block entries.
- Handwritten assembly without standard stack frames.

Stack frames, register-save patterns, and alignment are candidate evidence,
not proof.

Every word receives one of these classifications:

```text
proven_code
candidate_code
proven_data
candidate_data
conflict
unknown
```

Facts must be monotonic. A heuristic cannot overwrite contradictory proven
evidence.

## Phase 5: partition blocks into owners

Treat function recovery as a constrained partition problem.

Hard constraints:

- Every accepted block has exactly one owner within its bank.
- Owners do not overlap within a bank.
- Every direct call target is a callable entry.
- Ordinary fallthrough stays within its owner.
- Returns terminate paths.
- Tail transfers may cross owners.
- Shared tails and interior callable entries remain explicit.
- Banks may overlap in VA but never in identity.

Initial roots include:

- The ROM entrypoint.
- Proven direct-call targets.
- Thread and callback entrypoints.
- Proven function-pointer targets.
- Dynamically observed external entries.

Compute each root's reachable block closure. Competing closures create local
ambiguity regions. Normal cases should resolve through graph and interval
rules. SAT/SMT solving, if needed, should operate only on small connected
ambiguity regions rather than the entire ROM. Multiple valid solutions produce
an `open` result.

## Phase 6: resolve indirect transfers to a fixed point

> Implementation status (D2, 2026-07-16): static steps 1-5 are implemented in
> `fn64-discover::resolve` and driven to a fixed point by
> `build_cfg_value_set_closed`. The existing bounded HI/LO boot transfer is
> now one case in a finite abstract interpreter: up to 256 concrete values,
> register copies/arithmetic/shifts, exact stack/global word stores and loads,
> and joins across CFG blocks. A block that keeps growing after eight visits
> widens registers and tracked memory to unknown, which can only turn a site
> `open`; it cannot invent a target. These limits are mechanism, not tuning
> against an answer key.
>
> Switch recovery recognizes a `sltiu` upper bound selected by a dominating
> `beq`/`bne` edge, including the common compiler schedule where the scaled
> index (`sll index,2`) occupies the branch delay slot. HI/LO and GP-relative
> bases then produce a finite set of mapped word addresses; every entry must
> close to an aligned in-bank code target before the set becomes
> `exhaustive`. Partially usable finite sets are `bounded` and do not feed the
> CFG. A recovered `jr` table contributes ordinary intra-owner successors;
> its cases never enter `proven_roots` or the function-candidate stream. Only
> an exhaustive `jalr` set creates callable roots. Every reachable indirect
> site, including `bounded` and `open`, is serialized as an
> `IndirectTransferAnalysis` fact with construction kind, targets, and memory
> sources.
>
> This is derived from this document's Phase-6 rules plus public MIPS-III
> instruction/delay-slot behavior and the already-proven Phase-2 load-image
> bytes. No reference-runtime implementation source was consulted. Runtime
> observations (step 7) and mutable callback fields whose values arrive only
> through unknown arguments remain unimplemented and stay open.

The third-ROM NWXE answer-key run (2026-07-16) confirmed that the bounded
HI/LO resolver itself generalizes unchanged: from the header entrypoint
`0x80000400` alone, it resolves the stub's `lui $t2,0x8000` /
`addiu $t2,$t2,0x0460` / `jr $t2` sequence to resident entry
`0x80000460`. It did expose a separate generic Phase 4/5 over-split:
`build_cfg` promoted every direct `j` target to a callable root, but NWXE has
ordinary intra-function `j` targets that its generated disassembly records as
`alabel`s (for example `0x8002B92C` inside `osAiSetFrequency`). A direct `j`
proves code reachability, not a function boundary. The generic rule is now:
traverse a `j` target within the current owner unless independent evidence
(an explicit seed or direct `jal`) already proves that target is a callable
root. Corroborated tail calls still cross owners; uncorroborated jumps fail
closed as a coarser owner. On NWXE this removed five false splits and reduced
49 ambiguous blocks to zero without changing the resolver or adding any
game-specific discovery rule.

The D2 grading-only run over D1.5's same 469 proven OoT load images reports
230 exhaustive jump tables, 30 bounded constant computed jumps withheld from
closure, 105 open computed jumps, nine exhaustive constant indirect calls,
and 569 open indirect calls. Candidate precision/recall moved as follows:

- `JalTarget`: 5,486 candidates / 4,505 matches / 981 false positives /
  82.118119% precision before; 4,604 / 4,501 / 103 / 97.762815% after.
- `IndirectCallTarget` (new separate detector): 2 / 2 / 0 / 100%.
- `ProloguePattern`: unchanged at 8,637 / 8,612 / 25 / 99.710548%.
- Combined: 10,667 / 9,661 / 1,006 / 90.569045% precision and 72.323701%
  recall before; 9,789 / 9,661 / 128 / 98.692410% precision and the same
  72.323701% recall after. Ungradable claims fell from three to zero.

The grading-only false-positive audit did not feed discovery. Its dominant
finding was identity, not opcode decoding: calls from later overlays into the
resident-address range had been assigned to IPL3's initial one-megabyte boot
copy even when the later resident `code` image owning that VA is not among the
Phase-2 mappings. Cross-image calls now fail closed unless a non-boot mapping
exists; a reachable call may retain the initial-copy identity only for a
structurally delimited straight-line leaf. Raw `jal` words additionally need
two independent sites or a structural target boundary once multiple load
images exist. Of the 103 remaining `JalTarget` false positives, grading
classifies 41 as interior entries and 62 outside keyed function extents; 95
originate outside keyed function extents and eight inside. The former three
ungradable claims were targets in VRAM-only tails beyond their images'
VROM-backed bytes and are now withheld.

The recall result is deliberately reported as flat, not improved. Recovered
switch cases expose real CFG/ownership closure, but D1.5's linear `jal` and
prologue providers had already scanned those words. The two exhaustive OoT
indirect-call targets duplicate entries those providers already found. The
next honest OoT recall step remains the resident `code`/`n64dd` Phase-2
mapping frontier or new proof for the 569 argument/mutable-memory-derived open
calls; neither can be guessed inside Phase 6. NW4E improves from 89.040698% to
89.709302% combined recall and from 44.689233% to 48.438236% precision; NWXE
remains exactly 28.501229% recall / 36.363636% precision.

The NWXE stall was the predicted Phase-2 gap, not a detector gap: `gate_d1`
supplied no table geometry for NWXE, so detectors could only hunt the IPL3
boot copy while the answer key's four bank_text sections (~860 KB of the
key's code) sat in unexposed images. Wiring in the statically recovered
NWXE overlay bank table (aki-recomp `games/NWXE/overlays.json`, byte-verified
2026-07-17: 4 records × 0x24 at ROM 0x48a80, fields rom_start/rom_end/
vram_text at +0x00/+0x04/+0x08; banks 1/4 and 2/3 share VA slots with
disjoint ROM ranges) took NWXE to 86.855037% recall / 49.952897% precision —
parity with NW4E, from geometry input alone, zero pipeline changes.

For every computed `jr` or `jalr`:

1. Perform constant propagation and bounded value-set analysis.
2. Track HI/LO address construction.
3. Detect bounded jump tables.
4. Detect arrays of code pointers.
5. Track pointers copied through registers and memory.
6. Recognize callback fields using load/store provenance.
7. Add dynamically observed targets.
8. Re-run CFG and ownership closure.

Repeat until no new facts appear:

```text
new data pointer
    -> new table
    -> new code pointer
    -> new function root
    -> new CFG
    -> new references
```

Every indirect site records one of:

- `exhaustive`: all targets were proven from a bounded construction.
- `bounded`: the target universe is bounded, but some entries remain
  unresolved.
- `observed_only`: runtime targets exist, but exhaustiveness is not proven.
- `open`: no adequate resolution exists.

## Phase 7: generate targeted dynamic probes

Static analysis should automatically produce emulator probe plans for:

- Indirect calls without targets.
- PI DMA destinations with unknown bank identity.
- Suspected overlay activation.
- Code/data conflicts.
- Unreached executable candidates.
- Tables modified at runtime.

An instrumented emulator records:

```text
ordered sequence number
active bank set
PC
branch or call target
PI DMA source and destination
writes to suspected tables
exception and interrupt entry
```

Use existing checkpoints, scripted inputs, or coverage-guided execution to
maximize new blocks and indirect targets. Schedule probes by expected
information gain: an overlay activation that resolves hundreds of addresses
should precede an isolated leaf-function ambiguity.

## Phase 8: verify accepted metadata

For every accepted owner:

1. Emit matching assembly.
2. Assemble or link it at its expected address.
3. Compare every instruction word with the ROM.
4. Validate reconstructed relocations.
5. Confirm that every block and delay slot lies within the declared extent.
6. Confirm direct targets against the symbol catalog.

Then construct a complete address-accurate build using:

- Matching assembly for proven code.
- Bounded `incbin` regions for non-code or unresolved data.
- Independent link units for overlapping overlay banks.
- Linker assertions for addresses and sizes.
- A final exact-ROM digest gate.

An opaque interval may not hide code already accepted by the function catalog.
This prevents the full-ROM build from becoming a meaningless whole-ROM
`incbin` check.

## Acceptance gates

A metadata pack may claim static-code closure only when:

- Same-bank ownership overlaps are zero.
- Reachable uncovered blocks are zero.
- Invalid delay-slot classifications are zero.
- Unresolved direct targets are zero.
- Every accepted function has an exact ROM extent and byte digest.
- Every callable interior entry belongs to exactly one owner.
- Every bank mapping has evidence.
- Every indirect site is classified as exhaustive, bounded, observed-only, or
  open.
- Every ROM byte is classified or explicitly bounded as opaque.
- Repeated generation is byte-identical.

Open indirect sites do not block unrelated matching-decompilation work. The
per-function queue gate is closure of the symbols, relocations, and ABI facts
that affect that function.

## Efficient implementation

### Monotonic fact database

Store discoveries as immutable facts, for example:

```text
DirectCall(source, target)
BlockStart(bank, pc)
LoadsFrom(bank, pc, address)
ObservedIndirectTarget(site, target, trace)
RomMapping(bank, rom_start, va_start, size)
```

Use rules to derive higher-level conclusions. Datalog is a good fit for global
closure and provenance; decoding and per-function dataflow can remain in Rust.

### Content-addressed caching

Cache stages by:

```text
ROM digest
bank-map digest
analysis version
decoder version
configuration digest
input-fact digest
```

Changing one overlay decision should invalidate that bank and its dependents,
not the whole ROM.

### Parallelism

Parallelize:

- Independent banks and load images.
- Function CFG construction.
- Local dataflow.
- Signature providers.
- Assembly round-trip verification.
- Dynamic scenarios.
- Local ambiguity solving.

Workers should emit immutable facts. A deterministic merge sorts and
deduplicates them before deriving new state.

### Cheap-to-expensive scheduling

Run analysis in this order:

1. Direct CFG traversal.
2. Known-library signatures.
3. HI/LO and constant propagation.
4. Pointer- and jump-table detection.
5. Local ownership partitioning.
6. Assembly validation.
7. Dynamic probes.
8. Local constraint solving.
9. Human-supplied evidence only when the frontier remains open.

Most ordinary functions should close before expensive analysis begins.

## Relationship to decompilation

Function discovery and matching decompilation are separate layers:

```text
Target Pack
  bank-qualified execution identity and function ownership

Decomp Pack
  sections, data symbols, relocations, compiler profiles, and match proofs

Generated adapters
  Splat, linker scripts, assembly objects, m2c contexts, asm-differ and
  decomp-permuter jobs
```

A full set of semantic function names is not a prerequisite. Generated
identities allow assembly extraction, linking, relocation recovery, and C
matching to proceed. Semantic aliases can be added independently without
changing authoritative identity.

## Honest limit

A purely mechanical system can guarantee:

- Deterministic analysis.
- Exact provenance.
- No hidden uncertainty.
- Exact validation of accepted metadata.
- Efficient incremental closure.
- A finite, explicit unresolved frontier.

It cannot guarantee that an arbitrary stripped ROM contains enough static or
observed evidence to prove every unreachable function or every possible
runtime-generated target.

The optimization objective is therefore:

> Mechanically maximize proven metadata while minimizing and prioritizing a
> precisely defined unresolved frontier.

This provides a reusable, zero-LLM onboarding pipeline for new N64 ROMs while
preventing heuristic or human guesses from entering the authoritative function
catalog without machine-checkable evidence.
